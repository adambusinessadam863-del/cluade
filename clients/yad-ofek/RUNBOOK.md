## שלב 2: מספר הוואטסאפ [אתה + לקוח]: החלטה חשובה

הלקוח משתמש באפליקציית WhatsApp Business. זה משפיע על הכל.

### מסלול א׳: להשאיר את המספר הקיים (עובדים באפליקציה וגם האוטומציה)
- נקרא "coexistence". לפי התיעוד של Meta הוא זמין **רק דרך ספק או Tech Provider מאושר**, לא כהגדרה עצמית שלנו. ([Meta: onboarding business app users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users/))
- **לא אימתתי** איזה ספק תומך בזה בישראל ובאיזה מחיר. שואלים ספק (למשל 360dialog, Twilio, 8x8, Telnyx) שלוש שאלות: (1) האם תומך ב-coexistence בישראל? (2) כמה עולה בחודש? (3) האם ה-webhook שלו תואם ל-Cloud API ומאפשר כתובת משלנו?
- דרישות שמופיעות אצל ספקים: האפליקציה עדכנית, המספר רשום ב-Business (לא רגיל), פעילות רגילה בו כמה ימים (3–7) לפני החיבור, ואדמין בחשבון ה-Meta.
- מגבלות: שיחות קוליות לא זמינות, כמה פיצ׳רים של האפליקציה עלולים להפסיק לעבוד (רשימות תפוצה, קבוצות), והיסטוריה מסונכרנת חלקית. **לשאול את הספק לפני.**
- בשרת: `WA_MODE=bsp`, `WA_SEND_URL`, `WA_TOKEN`, `WEBHOOK_PATH=/webhook/<סוד>`.
- עלות נוספת: דמי הספק (ראו `COSTS.md`).

### מסלול ב׳: מספר חדש לאוטומציה, ישירות מול Meta (בלי ספק)
- האפליקציה הקיימת נשארת על המספר הישן, והאוטומציה על מספר חדש. **הלקוחות צריכים לדעת לפנות למספר החדש**: מוסיפים אותו לאתר, לכפתור וואטסאפ ב-Google Business Profile, לחתימה ולכרטיסים.
- המספר החדש (כרטיס SIM או מספר וירטואלי) לא יכול להיות רשום באפליקציית וואטסאפ.
- בשרת: `WA_MODE=meta`. אין דמי ספק.
- **המלצה לפיילוט:** אם בתוך שבוע אין ספק שמאשר coexistence במחיר סביר, מתחילים במסלול ב׳ על מספר חדש, ובודקים 30 יום. אפשר לעבור למסלול א׳ אחר כך.
- **אסור** להעביר את המספר הקיים ל-API על ידי מחיקתו מהאפליקציה בלי החלטה מודעת של הלקוח: הם יפסיקו לראות את השיחות באפליקציה.

## שלב 3: חשבון Meta (על שם הלקוח) [לקוח + אתה]
1. הלקוח פותח או משתמש ב-Meta Business Portfolio ומוסיף אותך כמנהל (**לא מעבירים סיסמאות**).
2. אימות עסק (Business verification): מסמכי העסק, בדרך כלל שניים או שלושה. השם והכתובת חייבים להתאים למסמכים. לוקח כמה ימים. (מקורות לא רשמיים סותרים בשאלה אם נדרש להעלאת מגבלת ההודעות. בדקו מול Meta.)
3. אפליקציה מסוג Business ב-developers.facebook.com, עם מוצר WhatsApp. (במסלול א׳ הספק עושה את זה.)
4. הוספת המספר ואישור שם תצוגה.
5. System User עם טוקן קבוע, והרשאות `whatsapp_business_messaging` ו-`whatsapp_business_management`.
6. שומרים: Phone number ID, App Secret, הטוקן. **שומרים רק ב-`.env` על השרת, לא בצ׳אט ולא בריפו.**
7. שולחים את התבניות מ-`TEMPLATES.md` ומחכים לאישור.

## שלב 4: שרת ופריסה [אתה]
(לא נבדק כאן: אין לי שרת ו-Docker לא רץ בסביבה שלי. הקבצים נכתבו לפי הנהלים הרגילים ו-`docker compose config` עבר.)
```bash
# על שרת Linux עם Docker (למשל Hetzner)
git clone <הריפו> && cd <הריפו>/clients/yad-ofek/deploy
cp .env.example .env && nano .env          # ממלאים. DOMAIN חייב להצביע על כתובת השרת ב-DNS
docker compose up -d --build
docker compose logs -f gateway             # מחפשים: "gateway פעיל"
```
- בהגדרות ה-webhook ב-Meta (או אצל הספק): Callback URL = `https://<DOMAIN>/webhook` (מסלול ב׳) או `https://<DOMAIN>/webhook/<סוד>` (מסלול א׳), ובמסלול ב׳ גם ה-`VERIFY_TOKEN`. מנויים על `messages`.
- התראות: הבעלים יוצר בוט ב-Telegram דרך BotFather, שולח לו הודעה, ואתם מקבלים `TELEGRAM_CHAT_ID`.
- כלי הצעות המחיר: `node clients/yad-ofek/build-quote-site.js` ואז מעלים את `dist/quote` לאחסון סטטי (למשל Netlify או GitHub Pages) ונותנים ללקוח את הקישור.
